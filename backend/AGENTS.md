# Правила и инструкции для подпроекта Backend

## Архитектура базы данных и представления (Views)

В базе данных PostgreSQL настроены представления для быстрого и удобного доступа к данным:

1. **`AsinView`**:
   - Назначение: удобная выборка товаров ASIN со штрихкодом EAN, ценой Buy Box и расчетной максимальной ценой закупки.
   - Поля:
     - `id` (Int, уникальный ID ASIN)
     - `asin` (String, код ASIN товара)
     - `ean` (String, штрихкод EAN производителя)
     - `brand` (String, название бренда)
     - `seller` (String, имя продавца из связанной таблицы Seller)
     - `buyBoxPrice` (Float, актуальная цена Buy Box)
     - `maxBuyPrice` (Float, максимальная цена оптовой закупки под 10% маржи)
   - Доступ через Prisma: `prisma.asinView.findMany()`

2. **`PrivateLabelView`**:
   - Назначение: просмотр связок брендов и продавцов (приватные лейблы).
   - Поля: `id`, `brandId`, `sellerId`, `brandName`, `sellerName`, `notes` (текст и результаты детального анализа связки), `createdAt`, `updatedAt`.

3. **`CandidatesProductsView`** и **`WholesaleCandidatesView`**:
   - Назначение: сводный анализ и группировка каталога под оптовую торговлю (Wholesale). Строго **1 запись на бренд и производителя** (`GROUP BY m.name, b.name, a."brandId"`). `WholesaleCandidatesView` является официальным синонимом (алиасом) к `CandidatesProductsView`.
   - Фильтрация: **строго исключаются** бренды, уже находящиеся в работе (`status = 'CONTRACTED'`, такие как Safta, Kuken, Cofan), а также бренды без дистрибьютора в ЕС (`status = 'NO_EU_DISTRIBUTOR'`), чтобы не засорять выдачу поиска новых позиций.
   - Сортировка: сначала отображаются бренды, у которых есть чистые товары (`cleanAsinCount > 0`, по убыванию `cleanAsinCount`), а ниже располагаются полностью отфильтрованные бренды (`cleanAsinCount = 0`, по `asinCount DESC`) для анализа после отработки основного пула.
   - Поля:
     * `manufacturer` (Text) — название производителя.
     * `brand` (Text) — название бренда.
     * `sellerCount` (Int) — количество уникальных продавцов бренда (индикатор рыночной Wholesale-конкуренции).
     * `sellerNames` (Text) — список всех продавцов через запятую (`string_agg`).
     * `cleanAsinCount` (Int) — количество чистых ASIN, подходящих для оптовой закупки (`filterReason IS NULL`).
     * `asinCount` (Int) — общее количество отобранных ASIN бренда.
     * `filterReasons` (Text) — причины отсева товаров бренда через запятую (или `NULL`, если все товары чистые).
     * `cleanAsins` (Text) — список только чистых ASIN через запятую для быстрого копирования и работы.
     * `asins` (Text) — список всех ASIN бренда через запятую.
     * `eans` (Text) — список штрихкодов EAN через запятую.
     * `distributors` (Text) — список привязанных дистрибьюторов через запятую.
     * `brandId` (Int) — ID бренда в таблице Brand.
     * `sellerIds` (Text) — список ID селлеров через запятую.

4. **`ContractedFilteredProductsView`** и **`ContractedAllProductsView`**:
   - Назначение: поштучный вывод товаров брендов, находящихся в работе (`BrandStatus = 'CONTRACTED'`), с расчетом чистой оптовой цены дистрибьютора (`netPrice`), себестоимости закупки с налогами (`grossPrice` / `costPrice`), комиссий Amazon (`amazonFees`), НДС на комиссии Amazon (`vatOnFees`: 21% IVA при авто-реперкуссии в Modelo 309, учитываемого в расходах на спецрежиме Autónomo Recargo de Equivalencia), чистой расчетной прибыли (`netProfitPerUnit`), ROI (%) и маржинальности (Margin %). Отсортирован по убыванию чистой прибыли.
   - **`ContractedFilteredProductsView`** (с фильтрами): включает жесткие оптовые критерии отбора: `salesRank <= 100 000`, доля присутствия Amazon в Buy Box `<= 50%`, `BuyBoxCurrent >= 10 €`, исключение мертвых вариаций.
   - **`ContractedAllProductsView`** (без фильтров): включает **все товары бренда в работе без каких-либо ограничений** по BSR (включая новинки с `salesRank IS NULL`), без фильтра по цене (товары дешевле 10 € также учитываются) и независимо от присутствия Amazon. Используется для поиска скрытых прибыльных позиций за пределами стандартных фильтров.
   - **Колонки ликвидности и статуса комиссий**:
     * `boughtInPastMonth` (Int): число покупок за прошлый месяц из официального бейджа Amazon («X+ bought in past month»). Позволяет мгновенно сортировать товары по подтвержденному спросу. Актуален только при дате снапшота Keepa не старше 1 месяца (30 дней); если выгрузка старая — ориентироваться на `estimatedMonthlySales`.
     * `estimatedMonthlySales` (Int): расчетная оценка продаж в месяц на основе количества падений ранга BSR в Keepa за последние 90 дней (`ROUND(salesRankDropsLast90Days / 3.0)`). Служит локальным аналогом Est. Sales (как в SellerAmp / Jungle Scout) и позволяет оценивать реальный темп продаж даже для позиций без бейджа Amazon.
     * `feeStatus` (Text / FeeCalculationStatus): статус жизненного цикла расчета комиссий и габаритов FBA:
       - `NULL`: товар только заведен в базу.
       - `KEEPA_REQUESTED`: поставлен в очередь запросов `RequestProductQueue` / `KeepaRequestQueue`.
       - `KEEPA_SUCCESS`: комиссии FBA и габариты успешно получены и подтверждены Keepa API.
       - `KEEPA_UNKNOWN`: Keepa ответил, но в базе Amazon габариты отсутствуют (`-1`), комиссии `null` (характерно для чистого FBM).
       - `SUPPLIER_ENRICHING`: запущен процесс обогащения габаритами из каталога/прайс-листа поставщика.
       - `SUPPLIER_SUCCESS`: габариты успешно найдены у поставщика, Size Tier и комиссии FBA рассчитаны.
       - `FAILED`: ни в Keepa, ни у поставщика найти габариты не удалось (неуспешный статус).
   - **Порядок сортировки по умолчанию**: во всех представлениях и функциях действует двухэтапная сортировка для строгой приоритизации ликвидных и прибыльных позиций:
     1. В самом верху отображаются **прибыльные товары (`netProfitPerMinBoxOrder > 0`)**: сортируются сначала по бейджу подтвержденных продаж `boughtInPastMonth DESC NULLS LAST` (быстрая оборачиваемость: 500, 200, 100, 50+ в месяц), затем по величине чистой прибыли с минимальной коробки `"netProfitPerMinBoxOrder" DESC NULLS LAST`, и затем по BSR `salesRank ASC NULLS LAST`.
     2. Товары с отрицательной или нулевой прибылью (`netProfitPerMinBoxOrder <= 0`) и позиции без расчета (NULL) не исключаются из выборки, а размещаются ниже всех прибыльных товаров (внутри своей группы они также упорядочены по `boughtInPastMonth DESC`, наименьшему убытку и BSR). Это гарантирует, что убыточные позиции не засоряют верх таблицы и не перекрывают прибыльные товары с меньшим числом заказов.
   - Дублирующее представление `ContractedProductsView` удалено; в системе используется чистая пара: `ContractedFilteredProductsView` (с фильтрами) и `ContractedAllProductsView` (весь каталог).
   - **Параметр переключения режима налогообложения**: SQL-функции `get_contracted_products(p_max_bsr, p_max_amazon_buybox, p_include_vat_on_fees)` и `get_contracted_all_products(p_include_vat_on_fees)` принимают флаг `p_include_vat_on_fees` (по умолчанию `TRUE` для режима Recargo de Equivalencia). При переходе на юридическое лицо (SL / Sociedad Limitada) или общий режим с вычетом НДС флаг переключается в `FALSE`, и `vatOnFees` перестает вычитаться из чистой прибыли.
   - **Правило приоритета цен (Current Price vs Buy Box)**: При детальном анализе привлекательности товара в приоритете всегда учитывается реальная текущая цена продажи на карточке товара (`Current Sale Price` в SellerAmp / `amazonCurrent` / `newCurrent`). Если на карточке сам Amazon выставил промо-цену со скидкой, покупатели ориентируются на нее, даже если Buy Box из-за отложенной доставки временно висит на стороннем продавце с завышенной ценой. Расчет по цене `Buy Box` рассматривается как вторичный альтернативный сценарий на случай, когда предложение демпингующего селлера/Amazon исчерпается.
   - **Обязательный контроль даты снапшота Keepa (Анти-устаревшие данные)**: При любом анализе товара ИИ **обязан** проверять и выводить дату последнего снапшота Keepa из таблицы `ProductFinder` / `KeepaApiProcessedData`. Если снапшот старше 48 часов или товар не попал в свежую выгрузку каталога (например, из-за просадки BSR свыше 5 000 строк выборки Keepa), дату **обязательно выделять красным цветом / предупреждением ⚠️ [ДАННЫЕ УСТАРЕЛИ]**, сигнализируя, что текущая цена полки и рейтинг продаж могли существенно измениться и требуют перепроверки на карточке. Свежие снапшоты маркируются зеленым цветом **✅ [АКТУАЛЬНО]**.

5. **`DistributorPriceSnapshot`**:
   - Назначение: хранение истории оптовых цен из прайс-листов поставщиков со связкой по `asinId` и `ean`, а также параметров кратности упаковки и минимального заказа.
   - Поля:
     * `distributorId` — связь с дистрибьютором.
     * `asinId`, `ean` — привязка к товару в базе.
     * `priceNetto` — оптовая цена без НДС.
     * `ecoTasa` — опциональный экологический сбор (эко-таса RAEE) за единицу электроники (в евро).
     * `costPrice` — себестоимость с испанскими налогами (IVA 21% + RE 5.2%):
       - При наличии эко-тасы (электроника KUKEN): `costPrice = round((priceNetto + ecoTasa) * 1.262, 2)`.
       - При отсутствии эко-тасы (SAFTA, COFAN): строго сохраняется `costPrice = round(priceNetto * 1.262, 2)`.
     * `unitsPerBox` — количество единиц в одной стандартной заводской коробке (`EMBALAJE` у Cofan, `UNI CAJA STD` у Safta).
     * `minBoxOrder` — минимальный объем партии закупки в **штуках** (`unitsPerBox * minBoxEnvases` для Cofan, где `ENVASE MÍNIMO` задает число коробок; либо прямое число штук в коробке для Safta).
     * `createdAt` — дата и время фиксации цены.
   - **Инвариантность цен при миграциях (Golden Snapshot Tests)**: В `src/prisma/db-functions.spec.ts` действуют строгие эталонные тесты, фиксирующие неизменность числовых показателей реальных строк Safta (`B01N4SDF1W`, `B0HFKT8N24`) и Cofan (`B08WM385FK`, `B00MGJ4GOO`). Любое искажение формулы или поломка отображения цен других производителей немедленно валит тестовый набор.
   - **Расчет минимальной партии в SQL-представлениях (`Contracted*View`)**:
     * `minBoxOrderGross = costPrice * COALESCE(minBoxOrder, unitsPerBox, 1)` — затраты брутто на выкуп минимальной партии.
     * `netProfitPerMinBoxOrder = netProfitPerUnit * COALESCE(minBoxOrder, unitsPerBox, 1)` — чистая прибыль с минимальной партии.
     * `profitCoefficient = netProfitPerMinBoxOrder / minBoxOrderGross` — коэффициент отдачи на капитал (чистая прибыль на каждый 1 евро вложений).
   - Быстрый поиск цен по ASIN или EAN: `npx tsx scripts/get-distributor-snapshot.ts <ASIN_или_EAN>` (используется навыком `analyze-product` для автоматического получения закупочных цен при анализе листингов).
   - **Автоматическая постановка в очередь анализа (`RequestProductQueue`)**:
     * При импорте прайс-листа дистрибьютора (`import-distributor-prices.ts`) все сопоставленные ASIN автоматически добавляются в `RequestProductQueue` с наивысшим приоритетом `999999`, чтобы получить свежие габариты, FBA Fee и комиссии в первую очередь. Несопоставленные EAN (новинки фабрики, отсутствующие на Amazon) сохраняются в файл `<дистрибьютор>_unmatched_eans.txt` для последующего анализа и потенциального заведения эксклюзивных карточек товаров с монопольным Buy Box. Повторная выгрузка через Keepa по ним не запускается, так как карточки физически еще не заведены на маркетплейсе.
     * При парсинге выгрузки Keepa (`parse-keepa.ts`) все новые добавленные ASIN бренда автоматически ставятся в `RequestProductQueue` с приоритетом `50`.
7. **Почтовая подсистема и CRM контакты поставщиков (`DistributorContact`, `DistributorEmail`)**:
   - Назначение: персистентная синхронизация входящих/исходящих писем из почтового ящика Hostinger (`imap.hostinger.com:993`) в PostgreSQL для мгновенного анализа коммерческих условий и истории общения без повторных запросов по сети.
   - **`DistributorContact`**: контакты и персональные менеджеры фабрик (`name`, `email`, `role`, `isPrimary`). Создается автоматически при получении писем от новых представителей.
   - **`DistributorEmail`**: история переписки (`messageId`, `distributorId`, `fromEmail`, `fromName`, `subject`, `date`, `bodyText`, `hasAttachments`, `attachments`). Защищена от дублирования уникальным `messageId`.
   - **Поле `domains` у `Distributor`**: массив доменов компании (`String[] @default([])`) для умного авто-связывания входящих писем от любых сотрудников фабрики.
   - **Скрипты**:
     * Синхронизация входящих: `npx tsx scripts/sync-emails.ts [--limit 30]`.
     * Поиск условий и переписки: `npx tsx scripts/search-distributor-emails.ts --distributor "<имя>" --query "<фраза>"`.
   - **Категорический запрет на отправку писем (Только чтение / Read-Only)**: ИИ **категорически запрещено** отправлять любые исходящие электронные письма (через SMTP, скрипты, почтовые API или любые другие каналы). Почтовая интеграция работает **строго в режиме чтения (Read-Only через IMAP)** для анализа входящей корреспонденции, условий поставщиков и скачивания вложений. Любые проекты ответов готовятся исключительно в виде текста для ручной отправки пользователем.
   - **Навык для ИИ**: `.agents/skills/distributor-emails/` активируется при вопросах об условиях доставки, минимальном заказе или переписке с менеджерами.

## Правила парсинга продавцов Keepa

- **Формат строки продавца в Keepa**: `Seller Name (80%) / SELLER_ID` или `Seller Name / SELLER_ID`.
## Архитектура персистентной очереди запросов Keepa (`KeepaRequestQueue`)

Для исключения исчерпания лимитов токенов Keepa и предотвращения потерь задач при рестартах реализована персистентная очередь запросов в таблице `KeepaRequestQueue`:
1. **Шкала приоритетов**:
   - `CRITICAL` (100) — любые прямые пользовательские запросы без крона (ручной запрос ASIN, выгрузка категории, каталога бренда или витрины продавца). Выполняются первыми и имеют право расходовать резервные токены.
   - `NORMAL` (10) — регулярный фоновый сбор сырых данных по товарам по крону (`fetchRawData`). Запускается только если токенов строго больше `10 + cost`.
2. **Неприкосновенный резерв токенов**:
   - Воркер очереди (`KeepaQueueService`) держит резерв минимум **10 токенов**.
   - Резервные 10 токенов расходуются **исключительно** на задачи с приоритетом `CRITICAL` (100). Задачи фонового крона (`priority < 100`) ждут накопления токенов свыше 10.
3. **Разделение обязанностей (Single Responsibility)**:
   - `KeepaQueueService` отвечает **строго** за управление очередью: добавление задач (`enqueueRequest`), мониторинг лимитов токенов и резерва (`tokensLeft`, `tokenReserveThreshold = 10`), приоритетный выбор и захват (`PENDING` -> `PROCESSING` -> `COMPLETED`/`FAILED`), диспетчеризацию `executeJob`.
   - `KeepaProductService` отвечает за сущность **товаров** (эндпоинт `/product`): управление оптовой очередью (`populateQueue`, фоновый запуск пачек `enqueueNextWholesaleAsins`), расчет лимитов пачки `calculateProductsBatchRequestLimit()`, запрос карточек товаров (`handleProductAsinsJob`), процессинг сырых данных в чистовик (`processRawData`, `processRawProduct`), расчет Size Tier.
   - `KeepaQueryService` отвечает за **поиск каталогов** (эндпоинт `/query` — Product Finder): выборка по категориям (`handleCategoryFinderJob`), брендам (`handleBrandFinderJob`) и продавцам (`handleSellerFinderJob`).
   - `KeepaService` выступает удобным фасадом для обратной совместимости, агрегируя оба сервиса.

## Логика фильтрации ASIN (`get_asin_filter_reason`)

Функция `get_asin_filter_reason(p_asin_id INT, p_dominant_threshold INT DEFAULT 90, p_min_winner_count INT DEFAULT 4)` возвращает причину отсева товара или `NULL`, если товар подходит:
1. `NO_BUYBOX_DATA` - отсутствуют снапшоты данных BuyBox по товару.
2. `BUYBOX_MATCH_BRAND` - имя продавца в BuyBox содержит название бренда.
3. `BUYBOX_MATCH_MANUFACTURER` - имя продавца в BuyBox содержит название производителя.
4. `PRIVATE_LABEL` - связка Бренд + Продавец подтверждена в таблице `PrivateLabel`.
5. `DOMINANT_BRAND_SELLER` - продавец удерживает Buy Box на >= 80% всех товаров каталога бренда в БД (проверка через функцию `check_brand_seller_dominance` при наличии обеих выгрузок Keepa). При отсутствии выгрузок в БД функция безопасно возвращает `false` (не выбрасывая исключений), что позволяет беспрепятственно выполнять фоновый первичный отбор кандидатов ASIN на сырых данных. Требование обязательного наличия обеих выгрузок валидируется на этапе углубленного ручного анализа связки через навык `verify-private-label`.
6. `FEW_BUYBOX_WINNERS` - количество победителей BuyBox за 90 дней (`buyBoxWinnerCount90Days`) строго меньше порога (по умолчанию `< 4` или `<= 3`, т.е. 1, 2 и 3 продавца отсеиваются; проходят товары только от 4 продавцов).
7. `DOMINANT_BUY_BOX_SELLER` - доля владения BuyBox у топового продавца за 90 дней (`buyBoxTopSeller90Days`, в БД хранится как `0.0..1.0`) `>= 0.90` (90%, листинг монополизирован). Функция автоматически приводит целый параметр (например, 90) к коэффициенту 0.90.
8. `NULL` - товар проходит фильтрацию.

## Система тегирования ASIN (ASIN Tags)

При обновлении данных ASIN через Keepa API (в `keepa-product.service.ts`) товар автоматически добавляется в очередь `AnalysisProductQueue`. 
Микросервис `AnalysisService` асинхронно анализирует ASIN на наличие вариаций и дату последней активности продавца в Buy Box.
1. `DEAD_VARIATION` — нет продаж/продавцов более 6 месяцев.
2. `MISSING_VARIATION` — нет продаж/продавцов более 3 месяцев (но менее 6 месяцев). Потенциальные эксклюзивы.
Эти теги сохраняются в поле `tags` таблицы `ASIN` и автоматически отфильтровываются в представлении `CandidatesProductsView`.

## Расчет максимальной цены закупки (`calculate_max_buy_price`)

Функция `calculate_max_buy_price(p_asin_id INT, p_target_margin_pct FLOAT DEFAULT 10.0, p_inbound_shipping FLOAT DEFAULT 0.40, p_vat_rate FLOAT DEFAULT 21.0)`:
- Вычитает испанский НДС 21% из цены Buy Box (`Net Price = BuyBox / 1.21`).
- Вычитает реферальную комиссию (`referralFee`) и FBA логистику Amazon (`fBAPickPackFee`).
- Вычитает входящую доставку (`0.40 €`) и целевую маржу (`10%` от чистой цены по умолчанию).
- Возвращает предельную оптовую цену закупки товара у поставщика (Netto, без НДС).

## Правила работы с миграциями Prisma и эталонными файлами

1. **Двойное внесение изменений (Эталон + Миграция)**:
   - При любом изменении SQL-функции или представления **в первую очередь** редактируется соответствующий эталонный файл в `backend/prisma/sql/` (чтобы в Git был виден чистый диф изменений объекта).
   - Затем создается заготовка новой миграции Prisma строго с флагом `--create-only`: `npx prisma migrate dev --create-only --name <name>`, куда копируется обновленный SQL код.
2. **Запрет на авто-применение миграций ИИ**:
   - ИИ обязан **только подготавливать** файлы миграции и SQL код, но **НИКОГДА самостоятельно не запускать применение миграций** (не запускать `npx prisma migrate dev` без `--create-only`).
   - Команду применения миграции выполняет строго сам пользователь.
3. **Целевая база данных**: Миграции применяются к базе данных, указанной в переменной окружения `DATABASE_URL` (в `backend/.env`). В текущей конфигурации она указывает на сервер на удаленном ПК (Huawei) в сети Tailscale. При выполнении команды `npx prisma migrate dev` изменения накатываются именно на эту удаленную базу данных.
4. **Неизменность существующих миграций**: Никогда не изменять старые файлы миграций в `prisma/migrations`.
5. **Единый регистр и нормализация Brand и Manufacturer (UPPERCASE + normalizeManufacturerName)**:
   - Все бренды и производители строго приводятся к верхнему регистру (`toUpperCase()`). В базе данных действуют регистронезависимые функциональные уникальные индексы (`Brand_name_upper_idx`, `Manufacturer_name_upper_idx`), предотвращающие появление дубликатов.
   - **Очистка производителей от вендор-кодов Amazon и унификация правовых форм (`normalizeManufacturerName`)**: При импорте названий производителей из выгрузок Keepa/Amazon обязательно применяется функция `normalizeManufacturerName`. Она отрезает технические коды Vendor Central в скобках на конце строки (`COFAN (COFB0)` ➔ `COFAN`, `MAMMUT (MAMQ3)` ➔ `MAMMUT`, `PURINA (PUTJ7)` ➔ `PURINA`) и унифицирует организационно-правовые формы компаний (`ALFA DYSER S.L` / `ALFA DYSER, S.L` ➔ `ALFA DYSER, S.L.`, `ACRYLICOS VALLEJO SL` ➔ `ACRYLICOS VALLEJO, S.L.`, `BELLOTA HERRAMIENTAS SLU` ➔ `BELLOTA HERRAMIENTAS, S.L.U.`).
6. **Согласование имен колонок в SQL со `schema.prisma` и рантайм-валидация PL/pgSQL**:
   - В PostgreSQL команды создания функций (`CREATE OR REPLACE FUNCTION ... LANGUAGE plpgsql`) проверяют только базовый синтаксис языка, но **не проверяют существование колонок таблиц внутри тела запросов**. Ошибки несовпадения имен колонок проявляются исключительно во время исполнения (при вызове функции или обращении к View).
   - При написании или изменении SQL-запросов и функций **всегда строго сверять имена колонок с моделью в `backend/prisma/schema.prisma`**. Например, метрики Keepa в таблице `ProductFinder` имеют формат: `amazon90DaysOOS`, `buyBox90DaysOOS` (число 90 идет перед `DaysOOS`, а не наоборот).
   - **Обязательные smoke-тесты**: Все SQL-представления и функции покрыты автоматическими smoke-тестами в `src/prisma/db-functions.spec.ts` (`SELECT * FROM "ViewName" LIMIT 1`). При добавлении новых Views или функций они обязаны добавляться в эти тесты, чтобы опечатки отлавливались на этапе `npm test` до применения на боевой БД.
7. **Парсинг процентов Keepa и расчет доли присутствия Amazon (`amazon90DaysOOS` / `calc_amazon_share`)**:
   - В выгрузках Keepa Product Viewer (`.xlsx`) ячейки процентов хранятся как математические доли от `0.0` до `1.0` (например, `1` = 100%, `0.56` = 56%, `0.01` = 1%), а в CSV — как строки со знаком `%` (`"100%"`, `"56%"`).
   - Для парсинга всех полей процентов и OOS (`Amazon: 90 days OOS`, `Used: 90 days OOS`) строго используется функция `parseKeepaPercentage()`, приводящая значения к шкале целых процентов `0..100`.
   - В SQL-функции `get_contracted_products` расчет `calc_amazon_share` обязан поддерживать как шкалу `0..100` (`(100.0 - OOS)/100.0`), так и историческую шкалу `0..1` (`1.0 - OOS`), чтобы товары со 100% отсутствием Amazon (OOS = 1 или 100) никогда не получали ложную долю Amazon 99%.


## Правила миграций данных (Data Migrations)

1. **Расположение**: Скрипты разового наполнения/обновления данных сохраняются в `backend/prisma/data-migrations/`.
2. **Именование**: `add-<subject>-<YYYYMMDDHHMMSS>.ts`.
3. **Добавление дистрибьюторов и связка с товарами**:
   - Поиск товаров по EAN производится напрямую в таблице `ProductFinder` (связь с `ASIN.productFinders`).
   - **Строгая 100% валидация**: количество найденных в БД товаров обязано строго равняться количеству переданных EAN (`foundAsins.length === targetEans.length`). При любом несовпадении или отсутствии хотя бы одного EAN скрипт выбрасывает исключение `throw new Error` со списком отсутствующих товаров и прерывает выполнение без сохранения неполных данных.
   - Запуск скрипта выполняется строго после явного подтверждения пользователем.

## Статусы воронки дистрибьюторов (DistributorStatus)

Для отслеживания коммуникаций с поставщиками в таблице `Distributor` используется enum `DistributorStatus`:
- `NEW`: Новый найденный дистрибьютор.
- `FORM_SUBMITTED`: Отправлена форма заявки на сайте.
- `EMAIL_SENT`: Отправлено приветственное B2B письмо.
- `CALLED`: Совершен звонок дистрибьютору.
- `ACCOUNT_OPENED`: Успех, B2B аккаунт открыт.

## Статусы бренда (BrandStatus)

Для глобальной классификации брендов в таблице `Brand` используется enum `BrandStatus`:
- `ACTIVE`: Активный бренд, участвует в оптовом анализе.
- `NO_EU_DISTRIBUTOR`: У бренда отсутствует официальная сеть B2B дистрибьюторов в ЕС. Товары автоматически получают `filterReason = 'NO_EU_DISTRIBUTOR'` в `get_asin_filter_reason` и исключаются из выдачи оптовых кандидатов (`CandidatesProductsView`).

## Маппинг вариаций производителей из Keepa (ManufacturerAlias)

1. **Назначение**: Связывает разнообразные сырые написания производителей из Keepa (включая вендор-коды Vendor Central Amazon в скобках, например `COFAN (COFB0)`, счетчики товаров в автодополнении, опечатки и вариации правовых форм `S.A.`, `S.L.`) с единым каноническим производителем в таблице `Manufacturer`.
2. **Таблица `ManufacturerAlias`**:
   - `id`: уникальный автоинкрементный ID.
   - `rawName` (`@unique`): сырое или Keepa-название в верхнем регистре (`UPPERCASE`).
   - `manufacturerId`: внешний ключ на каноническую запись в `Manufacturer`.
3. **Сервис `ManufacturerMappingService` (`src/keepa/manufacturer-mapping.service.ts`)**:
   - `cleanKeepaDropdownItem(str)`: отрезает число товаров в скобках на конце строки (`(28234)`, `(7178)`), добавляемое автодополнением Keepa.
   - `resolveManufacturer(rawName, client)`: сначала проверяет наличие алиаса в `ManufacturerAlias`. Если не найден — нормализует имя через `normalizeManufacturerName`, находит/создает `Manufacturer` и автоматически дополняет мапу новой записью `ManufacturerAlias`.
   - `getKnownAliases(canonicalName, client)`: возвращает список всех известных сырых вариаций для передачи в UI-фильтр Keepa.
4. **Интеграционные тесты (`src/keepa/manufacturer-mapping.spec.ts`)**:
   - Покрывают эталонные кейсы для производителей `COFAN`, `SAFTA`, `ALFA DYSER`.
   - Проверяют автоматическое распознавание и расширение мапы при появлении новых неизвестных карточек Keepa.

## Правила тестирования (Обязательное тестирование)

- **Обязательный запуск тестов**: При внесении ЛЮБЫХ изменений в исходный код `backend` или при подготовке новых миграций БД (изменение схемы, SQL-представлений, функций), ИИ **обязан** запускать тесты в `backend`, чтобы убедиться, что ничего не сломалось.
- **Обязательное покрытие автотестами любых конкретных кейсов и примеров пользователя (Test-Driven Edge Cases)**: Если пользователь сообщает о конкретной проблеме, краевом случае или приводит конкретный пример (например, нечувствительность к символам/акцентам, формат процентов, поведение валидации или расчеты), ИИ обязан создать отдельный воспроизводимый тест-кейс строго на русском языке именно на этот пример.
- **Эталонные тесты на основе конкретных снапшотов и строк («Прибивание гвоздями» / Golden Snapshot Tests)**:
  * Если разрабатывается новое бизнес-правило отбора/расчета или обнаружен баг на примере конкретной строки (ASIN, EAN, позиция прайс-листа или снапшот Keepa / дистрибьютора), ИИ **обязан написать автотест, буквально «прибивающий гвоздями» этот конкретный кейс с проверкой точных эталонных цифр**.
  * **Запрет абстрактных проверок**: Категорически запрещено ограничиваться поверхностными проверками (`toBeDefined()`, `toBeGreaterThan(0)`). Тест обязан сверять **точные числовые значения конкретной строки**: цены (`netPrice`, `grossPrice`, `costPrice`, `buyBoxPrice`), комиссии Amazon (`fbaFee`, `referralFee`), чистую прибыль (`netProfitPerUnit`), коэффициенты (`profitCoefficient`, `roiPercent`, `marginPercent`), кванты упаковки (`unitsPerBox`, `minBoxOrder`, `minBoxOrderGross`), продажи (`salesRank`, `estimatedMonthlySales`), долю Amazon (`amazon90DaysOOS` / `calc_amazon_share`) и причину отсева (`filterReason`).
  * **Защита от деградации бизнес-логики**: При любых будущих изменениях общих SQL-представлений, функций или формул эти тесты служат гарантом стабильности: если оптимизация или рефакторинг ломает поведение хотя бы для одной проверенной исторической строки, тест должен немедленно упасть и явно показать, какой именно кейс перестал работать.
- **Проверка перед завершением**: Проверка работоспособности тестов (что они успешно проходят) должна производиться ДО того, как ИИ отчитается о завершении задачи.
