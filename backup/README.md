# Резервное копирование и Disaster Recovery (Viasglobal)

Данный подпроект содержит единую инфраструктуру автоматизированного ежедневного резервного копирования всех баз данных кластера Viasglobal на сервере Huawei, трехуровневую систему проверки целостности (Healthcheck) и скрипты быстрого аварийного восстановления (Disaster Recovery).

---

## 1. Архитектура баз данных кластера

На боевом сервере Huawei (`100.92.50.18`) развернуты 3 независимых СУБД в изолированных Docker-контейнерах:

| Контейнер Docker | База данных | СУБД | Назначение | Примерный объем |
| :--- | :--- | :--- | :--- | :--- |
| **`backend-db-1`** | `viasglobal_db` | PostgreSQL 15 | Каталог Wholesale, товары, 100k+ ASIN, Keepa очереди, снапшоты дистрибьюторов | ~1.75 ГБ (дамп gzip ~830 МБ) |
| **`accruals-postgres`** | `accountant_db`, `watcher_db`, `telegram_bot_db`, `kvartplata_watcher` | PostgreSQL 16 | Сервис аренды: жильцы, квитанции, начисления, платежи, парсер ЖКХ | ~35 МБ (дамп gzip ~220 КБ) |
| **`ecommerce-db`** | `ecommerce_db` | PostgreSQL 16 | CRM/ERP система: закупки, поставщики, остатки складов, заказы | ~8.6 МБ (дамп gzip ~20 КБ) |

## 2. Структура файлов и скриптов

Все исполняемые джобы, скрипты и конфигурации crontab версионируются в репозитории:

```text
backup/
├── README.md                      # Данная подробная документация
├── AGENTS.md                      # Правила и команды для AI-ассистентов
├── cron/
│   ├── huawei.crontab             # Эталонный файл crontab для сервера Huawei
│   ├── install-cron.sh            # Скрипт установки crontab на сервер
│   └── mac-sync.sh                # Скрипт выгрузки/синхронизации бэкапов на Mac
└── scripts/
    ├── backup-all.sh              # Скрипт снятия дампов всех 3 БД и загрузки в S3/R2
    ├── check-health.sh            # Скрипт проверки свежести, размера, gzip и отправки алертов
    ├── restore.sh                 # Универсальный скрипт восстановления базы
    └── verify-checksums.sh        # Скрипт сравнения COUNT(*) и MD5-хешей данных
```

---

## 3. Расписание выполнения (Cron)

На сервере Huawei в планировщике `crontab` настроены три контрольные точки:

1. **`00:03` (каждую ночь)** — запуск [`backup-all.sh`](scripts/backup-all.sh):
   - Создаются свежие gzip-архивы для всех 3 баз данных.
   - Каждый архив немедленно тестируется на целостность (`gzip -t`).
   - Архивы выгружаются в облачное объектное хранилище (Amazon S3 / Cloudflare R2).
   - Локальные архивы старше 30 дней автоматически ротируются (удаляются).
   - Формируется отчет [`last_backup_status.json`](../../backend/backups/last_backup_status.json).
2. **`03:30` (каждое утро)** — запуск [`check-health.sh`](scripts/check-health.sh):
   - Проверяется свежесть файлов (<26 часов), минимальный размер и целостность CRC.
   - Отправляется heartbeat-сигнал в Healthchecks.io.
   - При сбое отправляется срочный алерт в Telegram владельцу (`743866013`).
3. **`12:00` (каждый день)** — дневной контрольный мониторинг [`check-health.sh`](scripts/check-health.sh).

---

## 4. Трехуровневая система проверки здоровья (Healthcheck)

1. **Telegram-оповещения**:
   - При сбое резервного копирования или обнаружении битого архива бот немедленно присылает сообщение владельцу в чат `743866013` с подробным описанием причины сбоя.
2. **Healthchecks.io Heartbeat**:
   - При успешном бэкапе отправляется пинг на контрольный URL `https://hc-ping.com/<UUID>`.
   - Если сервер завис, выключился или cron не сработал вовремя, сервис Healthchecks.io отправляет внешнее уведомление об отсутствии сигнала.
   - При явной ошибке скрипт шлет пинг с суффиксом `/fail`.
3. **REST API эндпоинт (`GET /health/backups`)**:
   - Внутренний эндпоинт бэкенда, возвращающий JSON со статусом, размерами и возрастом бэкапов. Доступен для автономных агентов OpenClaw и Hermes (описан в [`docs/SERVICES.md`](../docs/SERVICES.md)).

## 5. Быстрое аварийное восстановление (Disaster Recovery)

В случае полного выхода сервера из строя восстановить базу данных на новом сервере или локальном компьютере можно за 3 шага:

### Шаг 1. Получение последней копии бэкапа
Архивы доступны:
- В облаке Amazon S3 / Cloudflare R2 (`s3://${AWS_BACKUP_BUCKET}/...`).
- На локальном компьютере Mac в папке [`backend/backups/`](../../backend/backups/) (синхронизируется через `make backup-sync`).

### Шаг 2. Развертывание контейнера БД
Запустите чистый контейнер PostgreSQL:
```bash
docker run -d --name viasglobal-db \
  -e POSTGRES_USER=viasuser \
  -e POSTGRES_PASSWORD=viaspassword \
  -e POSTGRES_DB=viasglobal_db \
  -p 5432:5432 backend-db:latest
```

### Шаг 3. Импорт дампа одной командой
```bash
./backup/scripts/restore.sh --db viasglobal --container viasglobal-db
```
Скрипт автоматически найдет самый свежий архив, проверит его целостность через `gzip -t`, дождется готовности PostgreSQL и выполнит импорт.

## 6. Сверка идентичности по контрольным суммам (Golden Snapshot)

Для проверки того, что восстановленная база на 100% соответствует боевой базе на сервере, используется скрипт:
```bash
make backup-verify
# или напрямую:
./backup/scripts/verify-checksums.sh 100.92.50.18 5432 5435
```

Скрипт выполняет параллельную проверку:
1. Точного количества строк (`COUNT(*)`) по всем 22 таблицам.
2. MD5-хешей содержимого строк ключевых таблиц (`Brand`, `Manufacturer`, `Seller`, `ASIN`, `ProductFinder`, `DistributorPriceSnapshot`, `_prisma_migrations`).

Эталонные результаты сверки зафиксированы:
- **`ASIN`** (100,061 строк): MD5 `ea6b0a8248017b759486768cc9a98737` (100% совпадение).
- **`Brand`** (7,043 строк): MD5 `9561d1a716c715ecc2b8858b93718c07` (100% совпадение).
- **`Manufacturer`** (8,890 строк): MD5 `f78e0db7f9c74502aa0d196a1a70db44` (100% совпадение).
- **`Seller`** (5,314 строк): MD5 `e2f3a198d0ccd5d79871b1d7934cedf6` (100% совпадение).
- **`ProductFinder`** (128,106 строк): MD5 `a8f12b8ce0f279f617f97500d364a1f9` (100% совпадение).
- **`DistributorPriceSnapshot`** (7,549 строк): MD5 `db7c1f62db278037101d26ae325c1ec0` (100% совпадение).
- **`_prisma_migrations`** (94 миграции): MD5 `68a0bc9cf09bc6733979ebfea26cb7b7` (100% совпадение).
