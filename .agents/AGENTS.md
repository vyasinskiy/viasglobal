# Требования к проекту (Viasglobal) — Конституция проекта

Главные правила разработки, безопасности и взаимодействия автономных ИИ-агентов в монорепозитории Viasglobal. Специализированные правила подпроектов вынесены в локальные `AGENTS.md`.

- **Язык и комментарии**: Все комментарии в коде, документация (`README.md`), названия тест-кейсов (в `it`, `describe`, `test`) и инструкции для ИИ (`AGENTS.md`) пишутся строго на **русском языке**. В скриптах и коде обязательны подробные пошаговые комментарии на русском языке прямо над строками кода.

## 1. Безопасное чтение документов и запрет однострочников Python

- **Категорический запрет на однострочники `python3 -c "..."`**: Агентам **строго запрещено** запускать Python через флаг `-c`. Политика безопасности отключает префиксное сопоставление для флагов выполнения подкоманд (`-c`, `-e`, `--eval`) и принудительно запрашивает ручное подтверждение. Все операции выполняются через готовые CLI-скрипты.
- **Чтение PDF файлов**: Использовать системный инструмент `read_file` либо markdown-документацию. Запрещено запускать Python (`pypdf`, `pdfplumber`, `fitz`) для чтения PDF (библиотеки не установлены в системе и приводят к ошибкам).
- **Чтение Excel файлов (`.xlsx`, `.xls`, `.xlsm`)**:
  - Строго использовать универсальную CLI-утилиту [`scripts/read_excel.py`](file:///Users/usuario/code/viasglobal/scripts/read_excel.py) в режиме Read-Only.
  - Флаги: `--list-sheets`, `--headers-only`, `--search <текст>`, `--row <N>`, `--columns <колонки>`, `--format table|vertical|json`.

## 2. Модульная архитектура документации и реестр сервисов

- **Архитектура подпроектов**: Репозиторий разбит на независимые подпроекты (`ecommerce` (`backend`, `contractors`, `crm`, `docs`, `keepa`, `landing`, `shop`), `legal`, `openclaw`, `rent`, `viaslangs`, `backup`, `scripts`, `sms-gateway`). В каждом подпроекте есть локальные `AGENTS.md` (правила для ИИ) и `README.md` (документация).
- **Чтение локальных инструкций**: Если задача относится к подпроекту, ИИ **обязан первым делом прочитать локальный `AGENTS.md`** и `README.md` соответствующей директории.
- **Двойная документация**: При изменениях логики ИИ обязан синхронно обновлять оба файла подпроекта (`README.md` и `AGENTS.md`). Важные решения сохраняются в локальный `AGENTS.md`.
- **Принцип сквозной синхронизации знаний с OpenClaw (Knowledge Sync)**: Все бизнес-знания, регламенты, стандарты приемок, правила контрагентов, логистические выводы, форматы работы с налогами/Taxfix и уроки инцидентов, которым пользователь обучает любого ИИ монорепозитория, **в обязательном порядке должен знать OpenClaw**. При обновлении правил, навыков и регламентов ИИ обязан синхронно актуализировать системные инструкции OpenClaw (`openclaw/config/workspace/AGENTS.md` и `openclaw/.agents/AGENTS.md`).
- **Реестр микросервисов (`ecommerce/docs/SERVICES.md`)**: Вся архитектура контейнеров, сетей Docker, портов и REST API эндпоинтов хранится в `ecommerce/docs/SERVICES.md`.
- **Синхронное обновление API и деплой OpenClaw**: При изменениях эндпоинтов/портов в `backend`, `rent` или других сервисах ИИ **обязан обновить `ecommerce/docs/SERVICES.md`** и напомнить о деплое OpenClaw (`make redeploy-openclaw`), так как OpenClaw опирается на этот файл.

## 4. Защита от слепых изменений и подтверждение мутаций

- **Запрет на самостоятельный деплой и коммиты**:
  - ИИ **запрещено** выполнять команды деплоя (`make redeploy-...`, `docker compose up`, `deploy.sh` и т.д.) или применять миграции в боевую БД без прямого согласия пользователя.
  - ИИ **запрещено** делать коммиты (`git commit`) или пушить ветки (`git push`) без прямого согласия пользователя («Да», «Коммить»).
- **Запрет на мутации данных без подтверждения**: Запрещено самовольно создавать (`POST`, `INSERT`), изменять (`PUT`, `PATCH`, `UPDATE`) или удалять (`DELETE`) любые сущности в БД или через API.
- **Предварительное согласование**: Уточнить параметры -> Показать планируемое действие (сущность, поля, старое -> новое значение) -> Дождаться согласия («Да», «Создавай») -> Выполнить запрос.
- **Правила Google Tasks и Google Calendar**:
  - **Разграничение**: Дедлайны, проверки, follow-up задачи и чек-листы создаются **строго в Google Tasks (`task:create`)**. События календаря (`calendar:create`) разрешены **только для реальных встреч/созвонов** с фиксированным слотом времени.
  - **Запрет на удаление без спроса**: Перед `task:complete` или `delete` обязательно запросить подтверждение с объяснением причины.
  - **Follow-up Tasks**: При ожидании проверки документов или модерации создается задача в Google Tasks на крайнюю дату ожидания.
  - **Линкование задач**: Каждая запланированная задача линкуется в документации подпроекта: `[Название](https://tasks.google.com/task/<decoded_id>?sa=6)` (скрипт `calendar.ts`).
  - **Прямые ссылки**: В описаниях задач обязательно указывать прямые URL сервисов (`https://...` на TGSS, AEAT, Taxfix, Amazon, банк).
- **Учет счетов в Taxfix**: Фактура (`Factura`) загружается в Taxfix, связывается с выпиской (`Justificante de pago`), и создается задача в Google Tasks: `[Legal]: Taxfix — Загрузить фактуру <Номер> (<Поставщик>) и слинковать с банковской оплатой`.

## 5. Правила работы с Базой Данных (Prisma)

- **Чтение и запись**: ИИ разрешены только операции чтения (`SELECT`). Любые операции записи (`INSERT`, `UPDATE`, `DELETE`) или изменения структуры (`ALTER`, `DROP`) требуют предварительного согласия пользователя.
- **Нормализация Brand и Manufacturer**: Названия брендов (`Brand.name`) и производителей (`Manufacturer.name`) строго приводятся к `UPPERCASE` (`str.trim().toUpperCase()`). При импорте производителей применяется функция `normalizeManufacturerName` (отрезание вендор-кодов Amazon вроде `COFAN (COFB0)` и унификация форм `ALFA DYSER, S.L.`).
- **Неизменность миграций**: Старые файлы в `prisma/migrations` редактировать запрещено. Любые изменения структуры оформляются новой миграцией с флагом `--create-only` (`npx prisma migrate dev --create-only --name <name>`). Применение миграций выполняет строго сам пользователь.

## 6. Правила тестирования проектов и микросервисов

- **Обязательный запуск тестов**: При любых изменениях кода или подготовке миграций обязателен запуск автотестов соответствующего сервиса.
- **Test-Driven Edge Cases**: При сообщении пользователя об ошибке или краевом случае ИИ обязан написать отдельный тест на этот кейс на русском языке.
- **Golden Snapshot Tests («Прибивание гвоздями»)**: При доработке бизнес-логики или исправлении бага на конкретном товаре/снапшоте пишется тест с проверкой точных эталонных цифр (цены, комиссии, прибыль, ROI, Sales Rank, причина фильтрации). Поверхностные проверки (`toBeDefined()`) запрещены.
- **Проверка перед завершением**: Успешное прохождение тестов проверяется ДО финального отчета пользователю.
