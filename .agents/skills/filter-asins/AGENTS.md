# Инструкции для ИИ: Подпроект filter-asins

Этот файл содержит краткие правила и бизнес-логику для подпроекта фильтрации ASIN-ов. **Обязательно учитывай эту логику при написании кода или тестов.**

## Логика фильтрации (Доминирующий продавец)
При определении причины `DOMINANT_SELLER` в базе данных (`get_asin_filter_reason`) всегда используется двухэтапный алгоритм с порогом `p_dominant_threshold` (по умолчанию 80%):

1. **Этап 1 (Уровень ASIN):**
   - Получаем `sellerPercentage` из базы данных (таблица `AsinSnapshot`).
   - Если `sellerPercentage < p_dominant_threshold` -> продавец не доминирует, идем к другим проверкам.
   - Если `sellerPercentage >= p_dominant_threshold` -> переходим к Этапу 2.

2. **Этап 2 (Уровень Бренд+Производитель):**
   - Получаем общее кол-во ASIN-ов (`total`) для связки Бренд+Производитель текущего товара.
   - Получаем кол-во ASIN-ов (`seller_count`), где текущий `Seller ID` держит BuyBox.
   - Считаем долю: `(seller_count / total) * 100`.
   - Если `доля >= p_dominant_threshold` -> возвращаем причину `DOMINANT_SELLER` (фильтруем).
   - Если `доля < p_dominant_threshold` -> не фильтруем (продавец не монополист).
   - Если `total == 1`, то `доля == 100%` -> фильтруем.

## Логика Private Label (Бренд + Продавец)
Private Label теперь определяется как связка `Brand + Seller`, а не `Brand + Manufacturer`.
SQL функция обращается к таблице `PrivateLabel` по полям `brandId` и текущему `sellerId` из снимка. Если связь найдена, товар помечается как `PRIVATE_LABEL`.

> **Важно:** Всегда сверяй реализацию SQL-функций и интеграционные тесты (`db-functions.spec.ts`) с этим алгоритмом. Тесты должны покрывать как случаи, когда продавец забирает >80% ASIN-ов связки, так и случаи, когда он забирает меньше (например, реальный случай: 4 ASIN из 14 = 28% -> не фильтруем).
